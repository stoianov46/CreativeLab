# Translations (EN / RU / TH / HE)

**Status:** RU/TH/HE are LLM-drafted (2026-09-22) and **pending native
review** before launch — `proposal.md` rules out machine translation as
final copy. See `PROGRESS.md` → Phase 7.

## Where text lives

| What | English (master) | RU / TH / HE |
|---|---|---|
| Hub + service pages | `src/content/hubs/<hub>.ts` | `src/content/locales/<locale>/hubs/<hub>.json` |
| /services/* pages | `src/content/services/<slug>.ts` | `…/<locale>/services/<slug>.json` |
| /industries/* pages | `src/content/industries/<slug>.ts` | `…/<locale>/industries/<slug>.json` |
| /locations/* pages | `src/content/locations/<slug>.ts` | `…/<locale>/locations/<slug>.json` |
| Case studies / Journal articles | `src/content/case-studies.ts`, `src/content/journal.ts` | `…/<locale>/case-studies.json`, `journal.json` |
| Home, About, Contact, Portfolio, Case Studies, Journal, Privacy, Terms | `src/content/homepage.ts`, `src/content/pages.ts` | `src/content/locales/<locale>/pages.json` |
| Interface text (buttons, menu, form, section headings, footer) | `src/content/ui.ts` | `src/content/locales/<locale>/ui.json` |
| Language names in the switcher | `LOCALE_NAMES` in `src/content/i18n.ts` | — |

Each JSON file has the **same shape as its English source**, text only.
Every page, the header menu, footer, breadcrumbs, homepage cards and
related-service cards read through `src/content/translations.ts`, so:

- **Edit a string once and it changes everywhere it's shown.** A hub's or
  service's `navLabel` is its name in the menu, footer, breadcrumbs,
  homepage cards and related-service cards; there are no separate copies
  to keep in sync.
- **Anything missing or empty falls back to English**, so a
  half-translated file never breaks a page.

## Editing a translation

1. Open the JSON file from the table above and change the value (never
   the key).
2. Keep `{placeholders}` (`{hub}`, `{service}`, `{label}`, `{email}`),
   numbers/prices and `[[VERIFY: …]]` markers as they are.
3. `npm run dev` hot-reloads; open `/ru/...`, `/th/...` or `/he/...` (or use
   the language switcher in the header).
4. `npm run i18n:check` validates the result.

## When the English changes

Each translation file has a sidecar in `<locale>/.translated-from/<file>`: a
short hash of the English each string was translated from. So an edited English sentence shows up as
"needs translation" even though the old translation is still displayed.

1. Edit the English TS file as usual.
2. `npm run i18n:sync` adds new keys to every locale file (pre-filled with
   the English text), removes keys English no longer has, and regenerates
   `locales/<locale>/index.ts`. Translated strings are never overwritten.
3. `npm run i18n:check -- --verbose` lists every string that needs
   translating (new, or English changed since it was translated).
4. `npm run i18n:pending -- ru hubs/advertising.json` prints just those
   strings with their English, as JSON.
5. After translating: `npm run i18n:accept -- ru hubs/advertising.json`
   records the current English as the source, clearing them from the list.
6. A new content file (e.g. a new industry) needs no manual wiring:
   register it in its `index.ts` (English) and run `i18n:sync`.

`npm run i18n:export` writes the English source skeleton to
`.i18n-source/` (git-ignored). Hand that to a translator for a new pass.

## Merge rules (`src/content/localize.ts`)

- Only strings are translated. `slug`, `hubSlug`, `href`, `order`,
  `priority` and images are never read from translations.
- Arrays of items with a `slug` (a hub's `services`) are keyed by slug in
  JSON; every other array is matched by position.
- `translatableSkeleton()` (what the script exports and checks) and
  `localize()` (what the site reads) share these rules, so they can't
  disagree.

## Not translated (by design)

- `/llms.txt`, `/llms-full.txt`: English, for AI crawlers.
- `/api/contact` Telegram message labels: internal, for staff.
- Brand/product names (Google Ads, Instagram, FPV…) stay in Latin script.
